# CampusFix – Campus Incident Reporting App
 
A Flutter mobile app that lets ALU students report campus problems (broken facilities, water or electricity outages, damaged furniture, sanitation, safety) and lets authorized staff review reports and update their status until they are resolved.
 
Individual Assignment 2, Advanced Frontend, African Leadership University (ALU).
Author: Prince Ndahiro

## Features
 
**Students**
- Register with an ALU email, verify it by link, log in, log out, reset password
- Report an incident with category, title, description, campus location (building plus optional room) and an optional photo
- "Hide my name from other students" option (staff can still see the reporter)
- Browse all reports or only my reports, search by text, filter by category and status
- Report details with a status timeline and staff notes
- "Me too" button to say you are also affected, which helps spot duplicate reports
- Edit or delete your own report while it is still "Submitted"
**Staff**
- Staff dashboard with counts per status and a banner for open safety reports
- Queue sorted by urgency: open safety reports first, then oldest open reports
- Update a report's status (Submitted, Under review, In progress, Resolved, Rejected) with an optional note to the student
- Deep Pine app bar so staff can see at a glance that they are in the privileged role

## Architecture
 
```
UI (screens, widgets)  →  Providers (state, filters, commands)  →  Services  →  Firebase
```
 
Screens never call Firebase directly. `AuthProvider` holds the session and the user's role. `IncidentProvider` listens to Firestore once and every screen reads from it, so a status change made by staff shows up on every screen immediately.
 
```
lib/
  main.dart              app entry, MultiProvider, AuthGate
  firebase_options.dart  generated by FlutterFire
  core/                  app_config, validators, theme (colors, theme)
  models/                Incident, StatusEvent, AppUser, enums
  services/              AuthService, IncidentService, StorageService
  providers/             AuthProvider, IncidentProvider
  screens/               auth/, home/, incidents/, staff/, profile/
  widgets/               StatusChip, IncidentCard, IncidentPhoto, StatusTimeline, ...
  utils/                 formatters, UI helpers
assets/images/           campus.jpg (login header)
test/                    app_test.dart
firestore.rules          Firestore security rules
storage.rules            Storage security rules
```
 
`AuthGate` in `main.dart` routes by session state: loading, then login, then email verification, then the app.
 
## Firestore data model
 
```
users/{uid}
  name, email, role ("student" | "staff" | "admin"), createdAt
 
incidents/{incidentId}
  title, description, category, location, status
  photoData (base64 JPEG) or photoUrl + photoPath (Storage)
  reporterId, reporterName, isAnonymous
  affectedBy[]           user ids who tapped "Me too"
  staffNote
  history[]              { status, at, by, note }  status timeline
  createdAt, updatedAt
```
 
## Roles, access control and privacy
 
- Every user starts as `student`. The role lives in `users/{uid}.role`.
- Firestore rules stop clients from changing their own role, so staff accounts are created by editing the document in the Firebase Console.
- Access is limited to verified ALU emails (`@alustudent.com`, `@alueducation.com`) in both the app and the rules.
- Only staff can change `status`, `staffNote` and `history`. Students can edit or delete a report only while it is "Submitted". Any verified user can add or remove themselves from `affectedBy`.
- The staff dashboard and status controls are hidden from students, and the rules reject their writes even if the UI is bypassed.
- **Report visibility is a deliberate design choice.** All verified ALU users can read all reports. This lets students see whether a problem is already reported and use "Me too" instead of filing duplicates. A student can hide their name from other students, but the report content (title, description, location, photo) stays visible, so reports should not contain personal details.
See `firestore.rules` and `storage.rules`.

## Photos and Firebase Storage
 
Firebase Storage needs the paid Blaze plan, which this project does not use. By default photos are compressed on the device (about 900 px wide, JPEG quality 55) and stored in the incident document as base64. Photos over 600 KB are rejected so documents stay under Firestore's 1 MB limit.
 
The Firebase Storage upload code is included. To use it, set `AppConfig.useFirebaseStorage = true` in `lib/core/app_config.dart` and publish `storage.rules`. Nothing else changes.
 
## Requirements
 
Tested with: **Flutter 3.27.4 • Dart 3.6.2** (stable).
 
- **Flutter 3.27.4.** Newer Flutter releases can fail to compile the pinned `google_fonts` package. To install this exact version use FVM: `dart pub global activate fvm`, then `fvm install 3.27.4` and `fvm use 3.27.4`, and run commands as `fvm flutter run`.
- **JDK 17** (Temurin recommended). Newer JDKs such as 21 or 25 fail with this project's Gradle 8.3 (error: "Unsupported class file major version"). Set it with `flutter config --jdk-dir="<path to JDK 17>"`.
- Android Studio with an Android SDK (API 34 or newer) and an emulator, or a phone with USB debugging.
- The first build downloads Gradle and can take several minutes on a slow connection.
Platforms: Android (primary) and Chrome (development only). iOS is not configured.
 
## Getting started
 
```bash
git clone https://github.com/prince-nda/campus-incident-reporting-app.git
cd campus-incident-reporting-app
flutter pub get
flutter run                 # pick an Android emulator or device
flutter run -d chrome       # optional; photos use the browser file picker

```
 
The Firebase config files for the author's project (`google-services.json`, `firebase_options.dart`) are included, so the app runs without extra setup. Registration only accepts ALU emails, so use the test accounts from the report.
 
Firebase client keys are public identifiers, not secrets. Data is protected by Authentication, email verification and the security rules.

Download the APK from the GitHub Releases page (link at the top) and install it on an Android phone or emulator (`adb install app-release.apk`). No Flutter or Java is needed.
 
### Troubleshooting
 
| Problem | Fix |
|---|---|
| `Unsupported class file major version 69` or "Java 25 is incompatible with Gradle 8.3" | Install JDK 17 and run `flutter config --jdk-dir="<JDK 17 path>"`, then `cd android && ./gradlew --stop`, `flutter clean`, `flutter run` |
| `compilerOptions()` error in a `firebase_auth` build file | Use the pinned Firebase versions from `pubspec.yaml` (do not upgrade to the newest major versions) |
| `minSdkVersion 21 cannot be smaller than 23` | Already fixed: `minSdk = 23` in `android/app/build.gradle` |
| `google_fonts` constant evaluation error | Use Flutter 3.27.4 |
| `Can't find service: package` when installing | The emulator has not finished booting. Cold boot it and retry |
| `Connection reset` while Gradle downloads | Network problem. Rerun `flutter run` on a stable connection |
| Yellow and black stripes on screen | Flutter's debug overflow warning; the screen needs a layout fix, not a data fix |
 
### Using your own Firebase project
 
1. Create a Firebase project and run `flutterfire configure` (select Android and web).
2. Enable **Authentication → Email/Password** and create a **Firestore** database.
3. Publish `firestore.rules` in Firestore → Rules. Publish `storage.rules` only if you use Storage.
4. Adjust `AppConfig.allowedEmailDomains` and the domain pattern in `firestore.rules` if your emails differ.
5. Register an account, verify it, then set `role` to `staff` in `users/{uid}` to create a staff account.
Android needs `minSdk 23` (already set). The Firebase packages are pinned to versions that build with the current Gradle setup: `firebase_core ^3.8.0`, `firebase_auth ^5.3.4`, `cloud_firestore ^5.5.1`, `firebase_storage ^12.3.7`.

- Manual: registration with a non-ALU email, email verification flow, report submission with and without photo, search and filters, edit and delete rules, staff status updates, and role checks with a student and a staff account.
- Static analysis: `flutter analyze` reports no issues.
## Known limitations
 
- All reports (latest 300) are streamed once and filtered on the client. A larger deployment would need pagination or server-side queries.
- "Me too" lets any verified user edit the `affectedBy` array. A Cloud Function could enforce one entry per user.
- Staff cannot delete a student's photo from Storage because Storage rules allow only the owner.
- Photos in Firestore increase document size and read cost compared with Storage.
- No push notifications. Students see status changes live while the app is open.
- No rate limiting on report submission.
- iOS is not configured.
